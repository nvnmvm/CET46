# 登录加载状态日志排查

## 结论

本地已稳定复现：已经登录的用户进入账号页，再用同一个账号提交登录，后台成功但页面一直显示“正在检查登录状态…”。直接原因是前端加载状态没有结束，不是本次登录请求未返回。

此结论基于本地内存服务及当前源码；未读取生产服务器日志，不代表已确认线上每一次同类现象的原因。

## 请求证据

诊断日志：`/tmp/cet-login-diagnostic.log`。启用 `PREVIEW_LOG_REQUESTS=1` 后，测试服务只记录请求方法、路径、状态、耗时等元数据，不记录密码、请求体和 Cookie。

| 场景 | 日志证据 | 页面结果 |
| --- | --- | --- |
| 初次管理员登录 | req-7，POST /api/auth/login，200，约86毫秒；随后六个数据请求均200 | 正常进入管理员首页 |
| 管理员退出 | req-e，POST /api/auth/logout，200；随后 req-f 至 req-k 的六个旧数据请求全部401 | 回到登录页，却误报“登录状态已过期” |
| 真正退出后学习者登录 | req-l，POST /api/auth/login，200，约93毫秒；随后 req-m 至 req-r 均200 | 正常进入学习者首页 |
| 已登录的学习者再次登录同账号 | req-s，POST /api/auth/login，200，约102毫秒；没有紧随其后的数据加载请求 | 长时间停留“正在检查登录状态…” |

主代理通过浏览器实际操作并核对后台日志和浏览器网络响应。没有通过打印会话凭据来诊断。

## 代码因果链

1. `app/src/App.tsx:3342`：每次登录先执行 `setCloudLoading(true)`。
2. `app/src/App.tsx:3344`：服务器登录成功，返回用户。
3. `app/src/App.tsx:3345`：更新用户对象。
4. `app/src/App.tsx:3274`：负责加载数据并在 finally 关闭加载状态的 effect 只依赖 `user?.id`。
5. 同账号重新登录时 ID 不变，因此该 effect 不重新执行，`cloudLoading` 保持 true。
6. `app/src/App.tsx:3383`：`user && cloudLoading` 也渲染“正在检查登录状态…”，造成看似仍在检查登录的误导。

另一个已确认的问题在 `app/src/App.tsx:3358`：退出后调用 `refresh()`，但该函数仍捕获退出前的用户，向六个受保护接口发送请求，造成日志中的401。这是独立确认的问题；尚未证明它就是上一轮每次卡住的原因。

## 修复建议与验收

- 让每一次成功登录都有自己的数据加载和结束路径，不能只依靠用户 ID 变化；异常也须结束加载状态。
- 退出成功后不要再刷新旧账号数据，失效中的旧请求也不应影响新登录。
- 区分“检查登录状态”和“加载学习数据”的文案，方便用户和排查人员理解当前状态。
- 回归同账号重复登录、管理员退出后学习者登录、学习者退出后管理员登录、错误密码、刷新已有会话。
- 后台日志应看到登录成功后对应的数据请求结束；退出后不再出现由 refresh 主动引发的六个401请求。

## 修复后回归（2026-09-21）

已按最小范围修改 `app/src/App.tsx`：hydrate effect 改为依赖完整 `user` 对象；退出流程移除旧用户闭包中的 `refresh()`；成功登录后的首页跳转由父级 `App.login` 负责。

- 同账号管理员登录至少 3 次：均返回“今日”页；已有会话刷新后仍返回“今日”，显示管理员词库 3 词、进度 `0 / 3`。
- 管理员 → 学习者 → 管理员循环 2 次：均成功进入对应首页；学习者显示 `0 / 0` 词，管理员重新显示 `0 / 3` 词，确认词库隔离与管理员数据保留。
- 错误密码后重新填写正确学习者凭据：错误请求返回 401；正确请求返回 200 并进入学习者首页。
- 明确点击“退出登录”：页面回到未登录首页；日志显示 `POST /api/auth/logout` 为 200，未再出现旧 refresh 主动发出的六个 401。

主代理独立复核学习者同账号重新登录：正常返回 `#/` 首页。日志 req-ag 登录200（约64毫秒），紧随其后的 req-ah 至 req-am 六个数据接口均200，未停留加载状态。
