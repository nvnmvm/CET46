# CET 背词站改进方案：登录、用户数据存储与页面优化

版本：v1.1 · 日期：2026-09-19  
范围：按本轮最新要求，将重点收拢为前端登录体验、每个用户的账号及学习数据独立入库、现有页面优化。  
交付性质：方案文档；不代表已实现、已测试通过或已部署。

## 1. 目标与推荐路线

在保留现有背词功能和视觉风格的基础上，让网站成为可以供不同用户分别登录、保存个人数据、在不同设备继续学习的完整应用。

本期解决三个问题：

1. **登录好用**：界面清楚、操作流畅，刷新能恢复会话，错误和过期状态可理解。
2. **数据可靠**：账号信息、词库、学习进度、计划和草稿归属于相应用户，存入 MySQL；不同用户互相隔离。
3. **页面清晰**：优化首页、学习页、词库、导入、统计和个人页的信息顺序、布局与状态反馈。

推荐继续使用 React + TypeScript + Vite、Fastify + MySQL、1Panel/OpenResty。已有认证、数据库表和业务接口可继续使用，主要工作是接通前后端、补齐账号管理及数据迁移，再优化页面。

本期不更换复习算法，不新增大型题库、六种练习模式、AI 聊天或完整离线同步。现有新学、认词、拼写、斩词、备份等功能保持兼容。

### 1.1 账号范围

按“每个人有自己的账号和数据”设计多用户能力。推荐首期由管理员创建多个账号，用户分别登录；这与数据库支持多用户并不冲突。

公开注册属于独立产品选择：若后续需要允许任何人自助注册，再增加注册、验证、限流和账号恢复流程。本方案不把这些额外服务作为首期必做项，也不假定此前个人单账号约束仍覆盖新的多用户目标。

### 1.2 完成后的实际体验

- 用户 A 登录，看到自己的词库、计划和学习记录。
- A 在手机完成学习，在电脑重新获取数据后能继续。
- A 退出，用户 B 登录，同一浏览器不显示 A 的词条、统计或草稿。
- 新用户没有数据时看到导入引导，而不是别人的示例进度。
- 学习保存失败会明确提示并保留本次答案，不能显示虚假的“保存成功”。

## 4. 前端登录体验设计

### 4.1 登录页布局

建议沿用当前蓝色主色、圆角卡片与浅色背景，做一个独立、干净的登录页。

桌面端：内容区最大约 960px，左侧简短介绍、右侧约 400px 登录卡。介绍只呈现“真题词汇、学习进度、跨设备继续”三个已实现能力；云端数据验收前不写跨设备承诺。

手机端：单列卡片，左右 16—20px 留白。标题、邮箱、密码、登录按钮在主要可见范围；键盘弹出后按钮可滚动到达，不用固定高度导致遮挡。

```text
CET 真题背词
登录后继续学习

邮箱
[ name@example.com           ]
密码
[ •••••••••              显示 ]

[            登录            ]

账号由管理员创建，请使用已有账号登录。
```

生产界面不展示“Fastify、MySQL、服务器初始化”等实现细节。接入过渡阶段，数据位置说明放在合适的提示区域；接通后改为真实保存状态。

### 4.2 输入与交互

- 邮箱使用 email 输入类型、适当自动填充，去除首尾空格；密码保留原输入，不做 trim 或小写转换。
- 密码显隐按钮有可访问名称，切换时不清空内容、不提交表单。
- 支持密码管理器与粘贴；不在 localStorage 中记住密码或会话 token。
- Enter 提交；提交期间禁用重复动作，显示“登录中…”，按钮尺寸保持稳定。
- 错误提示就近显示且可被辅助技术读取；服务端返回“邮箱或密码不正确”，不暴露账号是否存在。
- 首期沿用后端已配置的会话有效期，不增加没有后端语义的“记住我”勾选框。
- 默认不出现不能工作的“注册”“忘记密码”链接。需要时展示管理员联系说明，具体联系方式由部署方配置。

### 4.3 登录状态机

| 状态 | 页面行为 | 数据处理 |
| --- | --- | --- |
| 正在检查会话 | 简洁加载态，避免先闪出错误用户页面 | 等待 `/api/auth/me` |
| 未登录 | 展示登录页 | 不加载私人业务数据 |
| 登录中 | 保留表单、锁定提交 | 不重复创建请求 |
| 登录成功 | 返回原本访问的站内页面或今日页 | 以服务端用户重新加载词库/设置 |
| 账号或密码错误 | 明确提示，可修改重试 | 不进入本地演示账号 |
| 网络或服务异常 | 提示“暂时无法连接，请重试” | 与密码错误区分 |
| 会话过期 | 提示重新登录，保留本机尚未提交草稿 | 重新认证后核对归属与版本 |
| 退出成功 | 返回登录页 | 取消请求、清空内存私有数据、撤销服务端会话 |

成功回跳仅允许已知站内路由，避免任意外部地址。退出请求失败时说明状态，不宣称服务端会话已撤销。

### 4.4 同一浏览器切换用户

服务端会话为唯一身份来源；不能把“浏览器里有一个 user 对象”当作已登录。

切换时中止或作废旧请求，清除页面词库、统计、查询缓存和草稿引用，再拉取新用户数据。旧请求晚返回也不得写入新用户页面。多个标签页共享 Cookie，使用广播通知或回到前台重新验证，不能在后台保留 A 页面后把操作发送到 B 会话。

有未提交答案时先提供保存/保留说明；本机草稿按账号隔离，不能给新账号恢复。主题、字体等纯设备偏好可以共享。

## 5. 每个用户的信息如何存入数据库

### 5.1 总体链路

```text
浏览器：页面、输入、临时交互
          │ 同源 HTTPS /api
          ▼
Fastify：验证会话 → 校验数据 → 根据当前用户执行操作
          │ 私有网络
          ▼
MySQL：账号、会话、词库、进度、设置、草稿与记录
```

前端不能直连 MySQL，也不能拿到数据库密码。后端从 Cookie 会话得到 userId；请求中即使出现其他 userId，也不能用它切换数据归属。

### 5.2 沿用已有表

| 表 | 保存内容 | 用户隔离方式 |
| --- | --- | --- |
| users | 邮箱、密码摘要、昵称、头像标识、时区 | 每账号独立 ID，邮箱唯一 |
| auth_sessions | 会话摘要、用户 ID、过期与撤销时间 | 当前会话关联唯一用户 |
| words | 单词、音标、释义、例句、来源 | `(user_id, normalized_word)` 用户内唯一 |
| word_progress | 阶段、认词/拼写分、到期时间、已斩状态 | 用户和词条复合关联 |
| learning_events | 新学、复习的时间与阶段记录 | 用户和词条复合关联 |
| user_settings | 每日目标、组数、每组词数、倒数日、时区 | 每用户独立设置 |
| review_drafts | 未完成学习队列与作答状态 | 用户 + draft key，带 revision |
| review_submissions | 完成请求的幂等结果 | 用户 + submission key 唯一 |

这些表已经在 migration 中定义，不需要从零建另一套 users 或 vocabulary 表。

A 与 B 都导入 `abandon`：各自生成个人词条及进度，A 的学习不影响 B。当前规模下继续这一简单模型；公共词库与个人进度分离可留到以后。

### 5.3 账号资料与管理

首期账号流程：管理员通过已有创建脚本为不同邮箱建立账号，用户通过登录页进入。无需先做一个管理后台。

建议最小新增项：

- 用户可更新自己的昵称、有限集合头像；沿用当前 avatar 标识，不默认加入文件上传服务。
- 增加修改密码入口：校验原密码，写新摘要，撤销旧会话并重新认证。
- 管理员可重置密码、停用/恢复账号，优先用受控命令完成；停用后撤销其全部会话。
- 若新增 status、password_changed_at 等字段，只追加 migration，不改已应用的历史 SQL。
- 邮箱变更先不开放，避免未经验证的新邮箱破坏账号归属。

密码摘要永不返回前端；个人信息接口只返回必要字段。初始密码和重置密码不写入命令参数、文档或日志。

### 5.4 数据位置约定

| 数据 | 权威位置 | 浏览器角色 |
| --- | --- | --- |
| 账号、会话有效性 | 服务端 | 仅使用 HttpOnly Cookie |
| 词库与学习进度 | MySQL | 加载后展示，提交成功再确认 |
| 每日计划、倒数日、昵称 | MySQL | 可编辑与刷新 |
| 学习草稿 | MySQL；失败时可保留本机恢复副本 | 账号隔离，带版本 |
| 主题、字体、声音选择 | 浏览器 | 设备偏好，不承诺跨设备 |
| 导入粘贴内容、当前输入 | 临时页面状态 | 提交前可恢复，退出时防串号 |

网络失败不能自动切回 localStore 并假装保存成功。首期采用服务器权威模式，完整离线学习不在本期范围。

## 6. 前后端接通方案

### 6.1 为什么不能简单替换一行

现在 `wordRepository = localStore`，页面大量同步读取数据，也在 useState 初始化器里读取草稿；apiClient 是异步接口，方法和返回结构不完全一致。

因此需要显式异步接口、适配器和页面加载状态。只把导出变量改成 apiClient 会产生 Promise、初始化、分页和错误处理问题。

### 6.2 分步接入

1. 分开设备偏好与用户业务数据：主题继续本地，词库/进度/设置走异步接口。
2. 先接通当前用户、设置和词库列表，完成加载、空状态、失败重试。
3. 接通导入、编辑、删除、斩词及恢复。
4. 接通新学、复习、独立拼写与草稿，保持原评分和间隔规则。
5. 接通统计、完整导出与旧数据迁移。
6. 本地适配器保留作兼容和回归，不作为生产出错时的静默回退。

分页接口现有每页最多 100 条，不能拿一页当全词库；搜索和筛选应在服务端对全部用户词条执行。统计不要依赖最近 5,000 条事件代表所有历史。

### 6.3 接口复用与缺口

| 能力 | 当前基础 | 建议动作 |
| --- | --- | --- |
| 登录/会话/退出 | 已有 `/api/auth/login`、`me`、`logout` | 继续使用，补页面状态和安全验证 |
| 词条读写 | 已有列表、导入、编辑、删除、进度动作 | 接入前端，补服务端筛选与批量删除 |
| 设置与事件 | 已有 settings/events | 接入设置，按日期聚合统计 |
| 学习提交 | 已有 new/review/spelling complete | 保持语义，处理幂等和冲突 |
| 草稿 | 已有 key + revision | 按新学/复习/拼写范围隔离 |
| 个人资料 | users 有字段，页面仍本地修改 | 拟增 `PATCH /api/account/profile` |
| 修改密码 | 当前无对应用户入口 | 拟增 `POST /api/account/password` |
| 迁移/完整导出 | 本地 v1 备份可用 | 拟增预检、提交、完整导出接口 |

新增路径是建议，实施时统一命名与返回格式。多个删除请求部分失败不能显示“全部删除成功”。

### 6.4 提交可靠性

同一轮提交的重试保持同一个 submissionKey。服务端应同时核对操作类型和请求摘要，相同 key 不同内容返回冲突。保存进度、事件、幂等结果在同一事务内执行。

草稿或进度版本冲突时提示另一设备已经更新，保留本机答案并重新获取数据；不直接覆盖。先采用提交后刷新、回前台重取，实现跨设备继续学习，不需要 WebSocket。

## 7. 旧浏览器数据迁移

登录改成服务器账号后，旧本地用户 ID 与新账号 ID 可能不同，即使邮箱相同也不会自然合并。迁移必须在接入上线前完成设计。

### 7.1 操作流程

1. 在旧站点导出 JSON 原始备份并保留。
2. 登录目标账号，选择备份文件，显示词数、进度、已斩数量和异常项。
3. 服务端根据当前会话绑定目标账号，不相信文件里的 userId。
4. 按规范词形建立旧词 ID 到新词 ID 的映射；进度、事件和草稿引用一起转换。
5. 展示新增、重复、内容冲突、进度冲突；目标已有进度默认保留，明确选择后才覆盖。
6. 幂等提交、事务写入，返回可核对报告。
7. 在第二台设备检查词库与进度，再切换正式仓储；不自动删除旧备份。

HTTP/IP/域名/HTTPS 可能是不同 origin，新地址不能直接读取旧地址的 localStorage，因此默认使用导出文件迁移。

### 7.2 兼容与恢复

当前 v1 包含词条、进度和学习事件，不包含完整设置、个人资料和草稿。新备份版本应明确纳入这些项目，密码与会话不导出；继续接受 v1，缺失字段采用明确默认值。

普通“词条导入”接口不能承担进度迁移。迁移是独立受控流程：小数据单事务，大数据先暂存验证后发布。重复导入同一批次不重复计分，不把不同设备的累计数直接相加。

切换后已产生新学习记录时，不能简单恢复旧数据库覆盖它们。先保存最新完整备份与增量，再按迁移报告恢复。

## 8. 页面优化方案

### 8.1 统一设计规则

保留当前浅蓝背景、蓝色主按钮、圆角白卡与深色模式，不全面换风格。

- 主按钮一屏一个重点，次级操作降为描边或文字按钮。
- 页面标题、区块标题、辅助文本采用统一层级；说明尽量靠近相关操作。
- 卡片内边距建议 16—24px，区块间距 24—32px；具体随手机/桌面调整。
- 主要点击区域至少按 44px 目标设计，输入框保持现有约 48px 高度。
- 抽取 Button、Input、Dialog、EmptyState、ErrorState、LoadingState 等实际复用组件。
- 手机保留紧凑导航，桌面放宽内容区；本期先不大改路由和导航名称。
- 动画用于按下、切换和反馈，尊重减少动态效果偏好。

### 8.2 各页面具体改动

| 页面 | 优化目标 | 拟改动 | 验收方式 |
| --- | --- | --- | --- |
| 登录 | 清楚、可信、易输入 | 精简说明、密码显隐、错误分类、会话检查与回跳 | 正误账号、断网、刷新、Enter、手机键盘 |
| 首页/今日 | 打开就知道下一步 | 草稿优先；突出待复习与今日新学；一个主 CTA；次要统计下移 | 用户可直接继续学习，数据与后端一致 |
| 学习页 | 减少干扰、避免丢答 | 固定信息顺序，阶段清楚；保存中/失败可见；按钮稳定 | 刷新恢复、重复点击、网络失败均可恢复 |
| 词库 | 更容易查找管理 | 搜索与筛选靠近；手机卡片/桌面紧凑列表；批量操作独立工具栏 | 超过 100 词仍可全库搜索与管理 |
| 导入 | 知道导入什么、错在哪里 | 保留 TSV 和手动入口；行号错误、预览摘要、进度与结果 | 同词不重置进度，失败不误报成功 |
| 统计 | 先看重点再看图 | 概览、阶段分布、趋势、复习安排；补文字摘要与时间范围 | 无数据/少数据/长历史均解释准确 |
| 我的 | 区分账号和设备设置 | 昵称邮箱、修改密码、计划、主题声音、数据备份、退出分区 | 更新后其他设备可见该同步的字段 |

### 8.3 首页建议结构

```text
你好，昵称                         头像
今天继续完成你的学习

[继续上次复习：还剩 6 词]          有草稿时出现

今日学习
待复习 32 词       今日新学 4/10
[开始复习]

词库 / 导入词汇 / 学习统计         次级入口
```

“待复习总数”和“本轮词数”要分清。学习计划改动不清空当前草稿，不改变现有复习规则。

### 8.4 学习页建议

保留新学、回忆、核对、拼写的现有区分。当前阶段明确显示进度，例句、来源作为辅助信息，避免答案提前泄露。

结果页显示完成数量、订正情况、下一次复习安排和保存结果。独立拼写不包装成完整认词复习，也不因为页面优化改变其调度语义。

支持键盘和触控：快捷键在输入框内不误触；弹层关闭后焦点返回触发点；手机键盘不挡住当前单词和提交操作。

### 8.5 统计页需先校准数据

当前趋势从时间窗口内累积，未带入窗口之前的各词状态；本地事件有 5,000 条截断。美化图表时应同时明确：

- 每日活动量与全词库历史阶段存量是不同指标。
- 历史存量需窗口前基线；没有完整历史时标明记录起点，不能反推过去。
- 新学、完整复习、独立拼写分开呈现，不将订正后成功当成首次正确率。
- 零分母显示暂无数据，图表有文字摘要与时间范围。

本期不引入复杂学习分析，只保证现有统计真实、清楚。

### 8.6 通用页面状态

每页都覆盖：加载中、空数据、无匹配结果、请求失败、会话过期、保存成功/失败。必要时保留旧数据显示更新时间，不能把请求失败伪装成空词库。

375/768/1024/1440px 检查布局；深色模式、200% 字体缩放、Tab/Enter/Esc 与屏幕阅读提示纳入验证。避免页面中暴露数据库结构、部署术语和内部错误文本。

## 9. 工程拆分与实施顺序

### 9.1 最小工程调整

当前 App.tsx 集中了多个页面。按职责拆出 LoginPage、HomePage、WordsPage、ImportPage、ProfilePage 和学习页面；入口只负责路由、会话与装配。

repository 从 `typeof localStore` 改为显式异步契约；保留 apiClient 做请求与 DTO 转换。加载/失败处理放入少量共享 hook/service，减少各页面重复实现。

继续使用现有 React 状态、Tailwind 与 Node test。无需为参考其他项目一次性添加 Zustand、Dexie、Recharts 或替换测试框架。依赖升级与业务接入分开进行。

### 9.2 分阶段工作包

## 10. 测试、部署与回滚

### 10.1 核心测试矩阵

| 场景 | 预期结果 |
| --- | --- |
| 正确/错误账号、网络失败、过期会话 | 提示准确，不误进入本地账号 |
| A 退出后 B 登录 | 看不到 A 的词、进度、草稿或统计 |
| A 请求 B 的 wordId、draft 或导出 | 服务端拒绝，数据库数据不变 |
| A/B 分别导入同词 | 各自拥有独立进度 |
| 同账号手机完成、电脑刷新 | 新进度、计划与草稿按契约一致 |
| 超过 100 个词搜索/筛选 | 覆盖用户完整词库 |
| 响应丢失后重试完成请求 | 只记录一次，返回原结果 |
| 两设备同时更新 | 冲突明确，不静默覆盖 |
| 迁移旧 v1 文件两次 | 第二次不重复新建或计分 |
| 备份损坏或中途失败 | 现有数据不受破坏 |
| 数据库备份恢复 | 核心字段与源备份匹配 |
| 手机键盘、深色、键盘导航 | 主流程可完成，焦点可见 |

继续执行现有 `pnpm test`、`pnpm run test:server`、`pnpm run typecheck:server`、`pnpm run build`。真实 MySQL 集成必须单独确认；没有数据库时的测试替身通过不等于生产验证通过。

现有 CI 已配置 MySQL service 与重复 migration，实施时核对实际执行结果。新测试聚焦跨用户隔离、异步恢复和迁移，不为纯样式调整添加镜像式测试。

### 10.2 发布前置条件

- 同源 HTTPS，Cookie Secure；API 与数据库保持私有访问路径。
- 校验登录限流、请求来源/CSRF 防护、日志脱敏和注销后的会话撤销。
- `/api` 错误返回 JSON，不回落到前端 HTML。
- 数据库增量与 API 先就绪，新版前端后发布，避免登录页面无法连接。
- Service Worker 不缓存 API；只清理本应用缓存，学习中更新先保存再刷新。
- 前端发布完整 dist，并保留旧资源/版本，避免缓存造成新旧资源混用。

上述是实施验收项，不能因已有 HttpOnly Cookie 就认为全部通过。

### 10.3 回滚与备份

发布/迁移前备份数据库和旧前端；先在测试库恢复验证。增量表结构尽量保持旧版本可读，避免上线即删除旧字段。

前端可回到上一兼容版本；有新业务写入后，数据库不能无分析地恢复旧快照。保存新数据、核对迁移报告后再处理。生产密码、会话密钥和账号凭据不进入仓库或交接文档。
