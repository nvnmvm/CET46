## 1. 文档用途

本文档专门负责“前端精简验收通过后，如何把网站部署到 1Panel”。前端结构调整、测试和代码拆分见 `project/docs/前端精简与部署交接文档.md`；服务器 + MySQL 的长期架构见 `project/docs/交接文档.md`。

本次部署不是数据库上线。它只把当前 React 前端构建成静态 HTML、CSS、JavaScript、图标和 PWA 文件，然后交给 1Panel 管理的 OpenResty 提供 HTTP 访问。当前使用公网 IP 直连，尚未绑定正式域名和 HTTPS 证书。

上线后仍然具有以下边界：

- 每台设备、每个浏览器、每个域名分别保存 localStorage 数据。
- 手机数据不会自动同步到电脑。
- `127.0.0.1`、`localhost` 和正式域名的数据互不共享。
- 当前“登录”仍是本机学习档案，不是服务器身份认证。
- 当前没有 Node.js API，也没有连接 MySQL。
- 当前不能宣传为云同步、云备份或多设备账号系统。

## 5. 域名和 DNS 准备

### 5.1 推荐域名形式

优先使用独立子域名，例如：

```text
words.example.com
```

当前 Vite 和 PWA 配置默认部署在域名根路径 `/`。不要在第一次部署时放到 `example.com/words/` 子路径；子路径需要同步修改 Vite `base`、manifest、Service Worker 和静态资源路径。

### 5.2 DNS

部署前在域名服务商处配置：

- IPv4 服务器：添加 `A` 记录指向服务器公网 IPv4。
- 确认使用 IPv6：再添加 `AAAA` 记录；服务器、云安全组和 OpenResty 都必须支持 IPv6。
- 暂不使用 IPv6：不要添加错误的 `AAAA` 记录，否则部分网络可能优先访问失败。
- 使用 CDN：先直连源站完成部署验收，再接入 CDN，避免缓存掩盖问题。

检查 DNS 时同时确认：

```bash
dig +short words.example.com A
dig +short words.example.com AAAA
```

文档中的 `words.example.com` 只是占位，执行时必须换成真实域名。

## 12. 阶段 G：OpenResty 静态配置

当前应用使用 hash 路由，`#/words` 中 `#` 后面的内容不会发送到服务器，因此域名根路径能返回 `index.html` 即可。保留 SPA fallback 仍有利于未来切换 history 路由。

项目已有参考片段：

```text
project/deploy/1panel/openresty.conf.example
```

当前静态阶段只需要静态 location。不要配置不存在的 API 上游。

建议逻辑：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}

location = /index.html {
    add_header Cache-Control "no-cache" always;
}

location = /sw.js {
    add_header Cache-Control "no-cache" always;
}

location = /manifest.webmanifest {
    add_header Cache-Control "no-cache" always;
}

location /assets/ {
    try_files $uri =404;
    add_header Cache-Control "public, max-age=31536000, immutable" always;
}
```

注意：

- 这是需要合并到站点现有配置的逻辑，不要在已有相同 `location` 时重复粘贴。
- 保存配置前先使用 1Panel 的配置检查；错误配置可能使 OpenResty 重载失败。
- hashed assets 可以长期缓存；`index.html` 和 `sw.js` 应及时重新验证。
- `/assets/` 不应回退到 `index.html`，否则丢失的 JS 可能返回 HTML 并产生 MIME 错误。
- 当前没有 `/api/` 服务，不要把 `/api/` 代理到空地址。

未来 API 上线后，才按项目示例添加独立 `location ^~ /api/`。API 错误必须保留真实状态，不能回退成 `index.html`。

## 13. 阶段 H：HTTPS 和网络

### 13.1 端口

云安全组和服务器防火墙至少确认：

- TCP 80：证书验证和 HTTP 跳转。
- TCP 443：HTTPS 网站。

不要因为静态网站开放数据库端口。当前部署不需要公网开放 3000、3306 或其他后端端口。

### 13.2 证书

在网站设置的 HTTPS 页面：

1. 选择已有证书或通过 1Panel 证书模块申请。
2. 确认证书域名覆盖主域名和实际使用的其他域名。
3. 开启 HTTP 自动跳转 HTTPS。
4. 验证自动续期。
5. HSTS 只在 HTTPS 稳定、全部子域策略明确后开启；开启后浏览器会长期强制 HTTPS。
6. HTTP/3 可后续启用，不应作为首次部署的必要条件。

PWA 的 Service Worker 在正式环境通常要求 HTTPS，localhost 是开发例外。因此 HTTPS 不是装饰项，而是完整 PWA 行为的前提。

## 14. 阶段 I：Service Worker 和 PWA

当前 Service Worker：

```text
app/public/sw.js
CACHE = cet-word-shell-v3
```

当前逻辑：

- 预缓存应用壳和图标。
- 页面导航优先访问网络，失败时回退 `index.html`。
- 同源静态资源优先读取缓存。
- `/api` 请求不会进入缓存。

每次发布都要检查：

1. `sw.js` 能通过 HTTPS 访问，状态为 200。
2. 响应 Content-Type 正确，不是 HTML fallback。
3. 浏览器 Application → Service Workers 显示当前作用域 `/`。
4. Cache Storage 中没有长期残留的过期 cache 名称。
5. 新 `index.html` 引用的新 hashed JS/CSS 能正常加载。
6. 离线重开只能保证应用壳可见，不能把当前 localStorage 版本描述成完整离线同步。

如果应用壳、manifest 或预缓存列表发生改变，应更新 `CACHE` 版本。不要每次无意义修改版本；但需要强制清理旧缓存时必须升级缓存名。

## 15. 阶段 J：正式域名数据迁移

浏览器按“协议 + 域名 + 端口”隔离 localStorage：

```text
http://127.0.0.1:4173
http://localhost:4173
https://words.example.com
```

这是三个不同的数据空间。部署后正式域名第一次打开通常没有原来的词库。

迁移步骤：

1. 在真正有数据的旧地址打开网站。
2. 导出 JSON 备份并确认文件落盘。
3. 导出 TSV 作为便于人工检查和批量编辑的副本。
4. 打开正式 HTTPS 域名。
5. 选择正确的本地档案。
6. 使用恢复功能导入 JSON。
7. 核对总词数、学习数量、到期数量、已斩数量、音标和释义。
8. 完成一次新学或复习后刷新页面，确认正式域名持久化正常。
9. 在确认正式域名稳定前，不删除旧地址的数据和备份文件。

不要通过复制浏览器内部 localStorage 文件实现迁移；使用应用提供的 JSON 导出和恢复，能经过格式校验和自动备份流程。

## 16. 阶段 K：上线验收

### 16.1 HTTP 与资源

将域名换成真实值：

curl -I https://words.example.com/manifest.webmanifest
curl -I https://words.example.com/icon-192.png

- `index.html` 和 `sw.js` 没有错误的长期缓存。
- JS 返回 JavaScript 类型，CSS 返回 CSS 类型。
- 缺失的 `/assets/not-found.js` 返回 404，而不是 `index.html`。

### 16.4 核心业务冒烟

使用少量专用测试词，不要直接拿唯一真实备份做破坏性测试：

10. 斩词、撤销和恢复。
11. 导出 JSON 和 TSV，确认浏览器产生真实文件。
12. 刷新、关闭标签页、重新打开，确认数据还在。

### 16.5 控制台和日志

- 浏览器 Console 无未解释错误。
- Network 无 JS/CSS/manifest/icon 404。
- 1Panel 正常日志有首页和资源请求。
- 1Panel 错误日志无持续 MIME、权限、循环重定向或证书错误。
- 不在日志中记录用户完整备份或敏感参数。

## 17. 阶段 L：发布后观察

首次上线后至少观察：

- 首次访问和重复访问速度。
- Service Worker 更新是否需要用户刷新两次。
- 手机添加到主屏幕后图标和启动页是否正常。
- HTTPS 证书续期任务是否正常。
- OpenResty 进程和磁盘空间是否稳定。
- 访问日志和错误日志是否异常增长。
- 用户是否误以为不同设备已经同步。

当前版本的数据主要在用户浏览器，服务器备份静态目录不会备份用户词库。必须继续依靠用户导出 JSON，直到后端和数据库真正上线。

## 18. 回退方案

### 18.1 需要立即回退的情况

- 首页白屏。
- 主要 JS/CSS 404。
- Service Worker 持续加载损坏版本。
- 登录、导入、学习或备份功能无法使用。
- 手机或电脑端出现阻断使用的布局问题。
- 新版本意外改变 localStorage 或备份格式。

### 18.2 静态回退步骤

1. 停止继续上传或覆盖文件。
2. 保存当前错误日志、浏览器控制台和问题版本发布包。
3. 将网站运行目录切回上一版完整静态包。
4. 检查 OpenResty 配置并重载，不要无必要重启整台服务器。
5. 使用无痕窗口验证首页和资源。
6. 检查 Service Worker；必要时临时指导测试用户刷新或注销旧 Service Worker。
7. 在本地源码中修复，重新完成生产构建与全部验收后再发布。

不要直接编辑服务器上压缩后的 JS/CSS。这样无法追踪，也会使本地源码与线上不一致。

### 18.3 数据说明

本轮要求前后版本保持 localStorage 和备份兼容，因此静态回退不应清空用户数据。不要把“清除站点数据”作为普通回退步骤；这会删除用户词库。只有用户已经导出并明确同意时，才能清理浏览器站点数据。

## 19. 未来后端上线边界

后续连接 1Panel 管理的 Node.js API 和 MySQL 时，继续采用同域：

```text
https://words.example.com/       → 静态前端
https://words.example.com/api/   → OpenResty 反向代理到 Node.js API
```

届时必须单独完成：

- 真实账号和 HttpOnly 会话。
- 后端环境变量和凭据管理。
- MySQL migration、用户隔离、事务和备份恢复。
- localStorage JSON 到正式账号的迁移。
- Service Worker 排除 API。
- `/api/` 不回退到 `index.html`。
- 后端端口仅走私有网络，不向公网直接开放。

浏览器永远不能直接连接 MySQL，数据库密码也不能放入 `VITE_*`、`dist/` 或前端源码。
